# Anima LoRA Training Tips

## Data preparation

### Dataset size recommendations

| Scenario | Minimum images | Recommended images | repeats |
|------|-----------|-----------|---------|
| Single-character LoRA | 30 | 50-100 | 10-20 |
| Style LoRA | 50 | 100-300 | 5-10 |
| Multi-character LoKr | 200 | 500+ | 1-3 |

### Image quality requirements

- **Resolution**: 1024×1024 or higher recommended
- **Cropping**: preserve the full composition as much as possible, avoid cutting off important parts
- **Diversity**: include different angles, expressions, outfits, and lighting
- **Consistency**: for a character LoRA, make sure the character's appearance stays consistent across images

### Caption quality

- When using a VLM to tag, check that the output is accurate
- Remove obviously wrong tags
- Keep tag style consistent (all lowercase, space-separated)

### Caption strategy paired with the regularization set

If you want the finished LoRA to behave like a **switch** — "trigger off → falls back to the base model's default / trigger on → produces the trained style or character" — the caption has to drop the "feature tags meant to be absorbed by the trigger" from the training captions; the regularization set then has to drop the trigger word too. Only when both sides work together does the trigger become a real on/off switch.

#### Core principle

| LoRA type | Keep in training caption | Drop from training caption | Excluded from regularization set |
|---|---|---|---|
| **Style LoRA** | Content tags (character / scene / objects) | — (leave as-is) | Trigger word + artist name |
| **Character LoRA** | Trigger word (character) + environment (scene / action) | Character features (hair color / eyes / build / signature outfit) | Trigger word (character name) |
| **Character + outfit LoRA** | Trigger word (character + outfit) + environment | Character features + outfit details | Trigger word (character name + outfit name) |

#### Why this pairing works

- Dropping feature tags from the training set's captions → the model binds those features **to the trigger**
- The regularization set's captions don't contain the trigger (the builder automatically excludes `based_on_version`; you can also manually add the trigger word / character name / outfit name to the regularization set's exclusion list)
- Regularization images come from booru's natural distribution or are self-generated by the base model, so hair color / eyes / outfit are **randomly distributed**
- During training, the regularization set supplies the supervision signal for "what this set of environment tags should look like when the trigger isn't present"
- The result: with the trigger off, output reverts to the base model's natural distribution; with the trigger on, you get the trained character/style

#### What happens if you don't follow this

If a caption still contains a feature tag that was supposed to be absorbed (e.g. training a character but not dropping `silver_hair`), then with the trigger off, writing `silver_hair` in the prompt will still leak the training set's style — the trigger stops being a clean on/off switch and behaves more like "weighted blending," and the LoRA tends to run into a trap where "not writing silver_hair actually makes things worse."

## Parameter tuning

### Learning rate

| Scenario | Recommended learning rate | Notes |
|------|-----------|------|
| Small dataset (<100 images) | 5e-5 ~ 1e-4 | Prevent overfitting |
| Medium dataset (100-500 images) | 1e-4 ~ 2e-4 | Standard range |
| Large dataset (500+ images) | 1e-4 ~ 3e-4 | Can be more aggressive |

**Debugging tips**:
- If loss decreases too slowly → raise the learning rate
- If loss oscillates heavily → lower the learning rate
- If overfitting (sample images get worse) → lower the learning rate or reduce epochs

### LoRA rank

| Rank | Parameter count | Best for |
|------|--------|----------|
| 8 | ~1MB | Simple style fine-tuning |
| 16 | ~2MB | Style LoRA |
| 32 | ~4MB | Single-character LoRA |
| 64 | ~8MB | Complex character / multi-character |
| 128 | ~16MB | Extremely complex scenes (rarely used) |

**Rule of thumb**: start with a low rank, raise it only if the result isn't good enough.

### LoRA vs. LoKr

| Type | Pros | Cons | Best for |
|------|------|------|----------|
| LoRA | Simple, stable, broadly compatible | Limited expressiveness | Single character, simple style |
| LoKr | Strong expressiveness, parameter-efficient | Needs more tuning | Multiple characters, complex styles |

### Optimizer choice

| Optimizer | When to use | Key parameters |
|--------|--------|---------|
| `adamw` | Default. For when you don't mind hand-tuning lr and want stable, predictable training | `learning_rate` starting at 1e-4 |
| `prodigy` | For when you don't want to tune lr. **Note**: prone to "style mutation epochs" on diffusion LoRA | `prodigy_d_coef` set to 0.5 for small datasets |
| `prodigy_plus_schedulefree` | **Recommended for DiT LoRA**. Adds Schedule-Free averaged weights on top of Prodigy; sample/save use the averaged weights, and **the style-mutation phenomenon largely disappears** | See below |

#### ProdigyPlusScheduleFree (PPSF) usage notes

Anima is Cosmos DiT + Flow Matching, which has the same class of issue as Flux/Qwen-Image. Those communities have already made PPSF the de facto default for LoRA training, because Prodigy's `d` estimate jitters under timestep randomness combined with small datasets, showing up as sample style mutations in certain epochs. PPSF smooths this out visually by maintaining averaged weights.

- **Learning rate**: fixed at `1.0` (PPSF internally estimates the real step size; the external lr is just a scaling factor; the UI enforces this)
- **lr_scheduler**: **must be `none`** (Schedule-Free has its own built-in schedule; stacking cosine on top breaks the convergence guarantee for the averaged weights; the UI disables this automatically and pydantic also rejects it)
- **ppsf_d_coef**: recommend `0.5` for small datasets (<50 images); `1.0` normally; try `2.0` if overfitting
- **ppsf_prodigy_steps**: recommend setting to 1/4 to 1/2 of total steps (e.g. 500-1000 out of 2000 total) to freeze `d` later on and prevent jumps; leave at `0` (never freeze) if unsure
- **ppsf_fused_back_pass**: turn on when VRAM is tight
- **save / sample behavior**: the training code automatically calls `optimizer.eval()` before sample and save to switch to averaged weights, then switches back afterward. The saved LoRA is in the averaged state and is ready to use directly

#### How to tell if switching from Prodigy to PPSF actually fixed your "mutation epoch" problem

Retrain the same dataset after switching, and compare samples from adjacent epochs:
- Before: style suddenly jumps away in certain epochs, then either returns or drifts to a new position in the next epoch
- After PPSF: samples should transition smoothly, with no visual "jump" discontinuity

If jumps still occur after PPSF, it's usually because `ppsf_d_coef` is too large, or the dataset itself is too small — try lowering it to `0.5` or `0.3`.

### Timestep sampling distribution

In Flow Matching training, each step samples a `t` from the `(0, 1)` interval to construct the noisy latent. Different distributions have a big effect on training results:

| Mode | Description | When to use |
|------|------|--------|
| `logit_normal` | The SD3/Anima default; biased toward the middle of `t`; `shift>1` pushes toward the high-noise end | Most cases, or if unsure what to pick |
| `uniform` | Uniform sampling, covers everything from the structural end to the detail end | Want the model to pay equal attention to all noise levels |
| `logit_normal_low` | Reverse-shifted logit-normal, biased toward the low-noise/detail end | Detail enhancement, style LoRA |
| `mode` | SD3's mode-distribution, concentrated around a particular sigma | Reproducing paper experiments |
| `mixed_uniform_low` | Each sample independently goes to `logit_normal_low` with probability `timestep_mix_low_prob`, otherwise uniform | Want detail enhancement while keeping uniform coverage |
| `mixed_uniform_logit` | Same as above but the biased branch uses `logit_normal` | Want a mild push toward high noise while keeping uniform coverage |

**`timestep_shift`**: only used by `logit_normal` / `mode`. `>1` biases toward high noise (structural end), `<1` biases toward the detail end. The default `3.0` is the SD3 empirical value.

**`timestep_mix_low_prob`**: only used by `mixed_uniform_*`, ignored by other modes. `0` = fully uniform, `1` = fully biased; typical values are `0.15-0.30`.

**`timestep_schedule_shift`**: acts on the **final t** (after sampling completes, it applies one more SD3/FLUX-style shifted-schedule offset, formula `t' = (t·s) / (1 + (s-1)·t)`, a Möbius transform); this is different from `timestep_shift`, which acts on the post-sigmoid u value inside logit-normal. The default `1.0` is the identity. `>1` pushes the whole distribution toward high noise; `<1` toward low noise. Can be stacked with any mode.

### Loss weighting

Weighting schemes change how much attention the model pays at different noise levels. **Only `min_snr` is broadly validated**; the rest are experimental:

| Mode | Best for | Key parameters |
|------|------|----------|
| `none` | Default, plain MSE | — |
| `min_snr` | **Strongly recommended**. SD3-paper approach, mitigates loss dominance at the t→1 end | `min_snr_gamma` defaults to 5.0, tune within 3.0~7.0 |
| `detail_inv_t` | Detail enhancement; loss ∝ 1/(t+ε), clamped to `[detail_inv_t_min, detail_inv_t_max]` | Default `[1, 5]` matches historical behavior; for hazy/low-saturation styles try `max=3`, for aggressive detail try `max=8` |
| `cosmap` | SD3-style cosine mapping | Experimental |

**`detail_inv_t_min` / `detail_inv_t_max`**: lower/upper bounds of the detail_inv_t weighting curve (default `1` / `5`).
- `detail_inv_t_min` must be ≥ `1.0` — because `1/t` for `t∈(0,1)` is always > 1, a lower bound below 1.0 would be a dead zone in the config.
- If `detail_inv_t_min > detail_inv_t_max`, schema validation errors out immediately at startup (fail-fast).
- Raising `max` makes low-t (detail-end) weighting more aggressive, but Prodigy users should note: overly large per-sample weights can dominate the `d` estimate, so it's recommended to also enable `weight_cap_ratio=5`.

### Loss function (new in 0.8.x)

`loss_type` defaults to `mse` (bit-for-bit consistent with historical behavior). `huber` is also available:

| Field | Default | Description |
|------|------|------|
| `loss_type` | `mse` | Choose `huber` for robustness to outliers, mitigating gradient explosions from extreme samples |
| `huber_c` | `0.15` | Huber δ coefficient (only for `loss_type=huber`); typically `0.1–0.3`, controls the quadratic/linear transition point |

**When to use huber**: when training occasionally produces NaN / loss spikes wildly, or the dataset has a small number of extreme samples. δ=0.15 is a common empirical value from the EDM/Karras papers.

**Note**: InfoNoise still receives plain MSE even when huber is enabled (decoupled by design), so the two can be used together.

### InfoNoise adaptive sampler (new in 0.7.1)

**InfoNoise is an adaptive timestep sampler based on I-MMSE information theory** (paper arxiv 2602.18647): during training it dynamically estimates the "information content" of each noise interval and concentrates sampling on the effective region, skipping the inefficient extremes of very high/low noise. In theory this speeds up convergence.

**When to enable**: for long runs (>2000 steps) once you're sure the baseline has already converged stably and you want to squeeze out more efficiency. For short runs / experimentation, leave it off (the default).

**Key fields** (visible in advanced mode):

| Field | Default | Description |
|------|------|------|
| `infonoise_enabled` | `false` | Enable switch |
| `infonoise_N_warm` | `0` | Warmup steps (`0` auto-picks 1/5 of total steps, minimum 200). During warmup it follows the baseline distribution chosen by `timestep_sampling`; afterward it switches to adaptive |
| `infonoise_K` | `64` | Number of bins in log-σ space; higher K = finer granularity |
| `infonoise_M` | `100` | Refresh the sampling distribution every M steps |
| `infonoise_B` | `256` | FIFO buffer size per bin |
| `infonoise_beta` | `0.9` | How strongly the adaptive distribution responds to the most recent batch. The FIFO already smooths things at a lower level, so a higher β is reasonable |
| `infonoise_N_min` | `50` | Minimum samples per bin required to trigger a refresh (must be ≤ `infonoise_B`) |
| `infonoise_gate_pivot_c` | `0.15` | Gate function pivot: noise below c gets sampled less. The default follows the paper's §5 CIFAR-reported value; set to 0 for fully adaptive selection |

**Checking whether it's working**: the wandb dashboard shows two metrics during training
- `infonoise/cdf_ready`: 1 = the adaptive CDF is ready, 0 = still in baseline mode
- `infonoise/refresh_degraded_count`: number of failed refreshes each time. If this stays 0 but `cdf_ready` also stays 0, it means your loss is already too uniform across log-σ (an already-converged model) — InfoNoise has no room to help, so just turn it off

**Note**: once InfoNoise is enabled, the `timestep_sampling` field is only used during warmup. In the main phase, the adaptive CDF takes over.

**Interaction with other training options**: InfoNoise uses unweighted MSE to estimate the information content of each noise interval; this is a necessary precondition of the paper's entropy-rate derivation. The table below lists configurations known to interfere with InfoNoise:

| Configuration | Interaction | Handling |
|------|------|------|
| `loss_weighting != none` (`min_snr`/`detail_inv_t`/`cosmap`) | Both mechanisms are reshaping the σ schedule (adaptive resampling vs. manual reweighting), and stacking them cancels each other out | Schema-mutually-exclusive; errors on config save |
| `loss_type=huber` | Huber clips outliers so they aren't learned as strongly, but InfoNoise still sees raw MSE showing those outliers as high → pushes more sampling mass toward them → feedback loop | Schema-mutually-exclusive |
| `timestep_schedule_shift != 1.0` | The shift only applies on the baseline path; once the CDF takes over, it silently stops having any effect | Schema-mutually-exclusive |
| `noise_enhancement_type != none` (`offset` / `pyramid`) | Noise enhancement changes the shape of the noise, so what InfoNoise learns is no longer the clean entropy-rate profile (the I-MMSE derivation assumes standard Gaussian noise) | Schema-mutually-exclusive |
| Regularization set (`reg_data_dir != null`, any `reg_weight`) | The reg set has a different distribution from the main set (typically general booru images vs. the LoRA subject); I-MMSE assumes a single distribution, so mixing them would make the schedule learn the mixture MMSE rather than mmse_main. InfoNoise hard-filters out reg samples using the batch's `is_reg` flag, so only main samples feed into the schedule learning; reg samples still participate in the gradient (weighted by `reg_weight`) | Handled transparently, no user action needed. If mainstream usage shifts toward multiple main distributions in the future (multi-concept LoRA), this will be reassessed per `docs/todo/infonoise-reg-policy-reeval.md` |
| LoRA dropout (`lora_dropout` / `lora_rank_dropout` / `lora_module_dropout`) | Adds gradient noise without introducing a systematic shift in the shape of the MSE | Can be enabled together; the FIFO + EMA double-smoothing can absorb it |

### Noise enhancement

| Field | Default | Purpose |
|------|------|------|
| `noise_enhancement_type` | `none` | Choose one of `none` / `offset` / `pyramid`. Keep at `none` by default for LoRA training |
| `noise_offset` | `0.0` | DC offset strength (0-0.2, 0=off). Shifts the noise mean away from 0, giving the model a chance to learn to generate extreme-brightness scenes (pure black / pure white / strong contrast). Typical range 0.05-0.1 |
| `pyramid_noise_iters` | `0` | Number of pyramid noise layers (0-6, 0=off). Each layer injects noise at scale `spatial // 2^(k+1)`. **The actual effect strength is determined by `pyramid_noise_discount`** — iters alone just determines the range of frequency bands covered |
| `pyramid_noise_discount` | `0.5` | Per-layer relative decay coefficient (0.1-0.9). **The key parameter controlling low-frequency strength**: anima normalizes the overall noise std back to 1. 0.1-0.4 is close to standard Gaussian after normalization, effectively equivalent to off; 0.5-0.7 noticeably changes the low-frequency structure |

**Mutual exclusion constraint**: `noise_offset` and pyramid noise **cannot be enabled at the same time**. Both are injecting low-frequency components into the noise (pyramid's lowest-resolution layer is roughly equivalent to `noise_offset`), and stacking them would inject low-frequency content twice, distorting the training target. This matches the hard constraint upstream in kohya's [sd-scripts PR #477](https://github.com/kohya-ss/sd-scripts/pull/477). Anima's schema validation forces the opposing field to zero; if an old yaml has both enabled, it's mapped to prioritize pyramid whenever `pyramid_noise_iters > 0`.

### Flip augment + cache latents (double caching)

When `flip_augment` and `cache_latents` are both enabled, Anima follows kohya upstream's `latents` / `latents_flipped` pattern and stores **double the latents**:

- during the cache phase, each image is encoded twice (original + mirrored), stored separately under the `latent` / `latent_flipped` keys in the npz
- at training time, `__getitem__` picks the flipped version with 50% probability, matching the behavior of the non-cache path
- cost: **both encoding time and cache size double** (unnoticeable for small datasets, worth weighing for large ones)
- an old cache (with only `latent`) combined with `flip_augment=true` is automatically detected as invalid and re-encoded to fill in the gap; switching back to `flip_augment=false` doesn't trigger repeated re-encoding (the double version is a superset of the single one)

Historical bug: before version 0.11.x, enabling both at once baked the cache phase's single random flip into the npz, **permanently disabling flip_augment and permanently corrupting 50% of the data with mirroring**. This was fixed in 0.11.x with the double-cache scheme; existing corrupted caches are automatically detected and re-encoded via `_is_cache_valid`.

### Default value changes (0.7.0 → 0.8.0)

The following field defaults changed. **Old presets that explicitly set a value are unaffected**; those relying on the default should note the pacing changes:

| Field | Old default | New default | Effect |
|------|--------|--------|------|
| `save_every_epochs` | 0 | **2** | Saves a LoRA every 2 epochs |
| `save_every_steps` | 500 | **0** | Step-based saving off by default |
| `save_state_every_steps` | 1000 | **0** | Step-based state saving off by default |

Old yamls using `save_every` / `save_state_every` still load fine (the schema auto-migrates them to the new names).

## FAQ

### Overfitting

**Symptoms**:
- Training loss is very low, but sample image quality degrades
- Generated images look almost identical to the training set
- No longer responds to new prompt variations

**Solutions**:
1. Reduce epochs
2. Lower the learning rate
3. Increase tag_dropout (5-15%)
4. Lower the LoRA rank
5. Increase data diversity

### Underfitting

**Symptoms**:
- Training loss stays stubbornly high
- Sample images show no sign of the target features
- Character/style doesn't resemble the target

**Solutions**:
1. Increase epochs
2. Raise the learning rate
3. Raise the LoRA rank
4. Check whether the tags are correct
5. Check whether the data is loading correctly

### Character collapse

**Symptoms**:
- Character features are unstable
- Sometimes correct, sometimes not
- Multiple characters get confused with each other

**Solutions**:
1. Make sure each character's tags are consistent
2. Increase the weight of the character name tag (at inference time)
3. Use keep_tokens to protect the character name
4. Increase the amount of training data

### Out of VRAM

**Symptoms**:
- CUDA out of memory
- Training interrupted

**Solutions**:
1. Enable `grad_checkpoint: true`
2. Reduce `batch_size` (compensate with `grad_accum`)
3. Lower `resolution`
4. Disable `cache_latents` (will be slower)
5. Use `mixed_precision: bf16`
6. Enable **block swapping** (`blocks_to_swap`): keeps later DiT layers in system RAM and moves them to VRAM only when needed for compute. Anima saves roughly 0.13GB per layer; swapping out all 28 layers lets training run on a 6GB-class GPU (at 1024², with sampling still on, at about 11% slower).  Swapped-out layers need an equal amount of **pinned (page-locked)** memory, so make sure you have enough headroom.

### Training suddenly slows down mid-run, VRAM fills up but no OOM (Windows)

**Symptoms**:
- Speed is normal for the first few dozen steps, then it/s drops by more than half after a certain step and never recovers
- Task Manager / `nvidia-smi` shows dedicated VRAM maxed out, and "shared GPU memory" starts climbing, but there's no CUDA OOM
- In the logs, torch's "allocated" isn't high, but "reserved" and total card usage are much higher than that

**Cause**: Windows WDDM allows CUDA allocations that exceed dedicated VRAM to spill into system memory ("sysmem fallback"), after which every step has to move data over PCIe. On Linux, the same scenario would trigger PyTorch's allocator self-healing cycle of "OOM → free cache → retry"; on Windows, the allocation never fails, so that self-healing never kicks in. Multi-resolution bucket (ARB) training is especially prone to this: when switching to a new bucket, the cached segments left over from the old bucket stack on top of the new bucket's activation peak, and reserved memory can jump 30% in one go.

**Fix**:
- The trainer automatically returns the previous bucket's allocator cache when switching buckets, so no extra setting is needed for multi-bucket training.
- If the same symptom shows up in other paths like image generation or evaluation, you can go to the NVIDIA Control Panel → Manage 3D Settings → Program Settings, and set Python's "CUDA - Sysmem Fallback Policy" to "Prefer No Sysmem Fallback": allocations beyond the limit will then fail with a direct OOM, and PyTorch's self-healing path kicks in; the tradeoff is that genuinely oversized scenarios that used to be "slow but working" will now fail outright.

### CUDA out of memory at startup, even though there's plenty of VRAM

**Symptoms**: with block swapping enabled, it reports `CUDA error: out of memory` before even a single layer has been loaded onto the GPU.

**Cause**: this isn't actually VRAM, it's **host pinned memory** (`cudaHostAlloc`). The weights for swapped-out layers need to be pinned in system memory, and Windows has a system-wide cap on pinnable memory (empirically, roughly half of physical RAM).

**Fix**: reduce `blocks_to_swap`, or close other memory-hungry programs. The error message now states directly that it's pinned memory, and how much it was trying to pin, instead of a generic CUDA out of memory message.

## Monitoring training

### Reading the loss curve

```
Ideal curve:
  Fast drop → slow drop → plateau

Overfitting curve:
  Fast drop → keeps dropping → very low (near 0)

Underfitting curve:
  Slow drop → stalls → stays high
```

### Checking sample images

Check sample images every few epochs:

1. **Early** (epochs 1-5): the target features should start appearing in rough form
2. **Mid** (epochs 5-15): features should become increasingly clear
3. **Late** (epochs 15+): quality should stabilize; watch for overfitting

### Using the training monitor

Go through Studio's monitor page: after starting training, open <http://127.0.0.1:8765/studio/tools/monitor>, or go to the **⑥ Training / Queue** page, click a task, and open **Task Details → Monitor**.

The monitor panel shows:
- Live loss curve
- Learning rate changes
- Sample image previews
- Training speed

> The old `python train_monitor.py`, which ran its own HTTP server, has been removed (see the docstring at the top of `runtime/train_monitor.py`); it's now just a status writer called by `anima_train`, and no longer needs to be started separately.

## Hardware optimization

### LyCORIS 4 fused kernels (Windows / NVIDIA)

The project uses LyCORIS 4.0, and on Windows it automatically picks the correct Triton build to match the installed PyTorch version; for example, PyTorch 2.11 pairs with `triton-windows 3.6`. At startup you should see something like:

```text
[studio] LoRA kernels: LyCORIS 4.0.0 · preferred=triton · fused=triton · Triton 3.6.0.post26
```

The backend is chosen automatically per call: Triton → TileLang → `torch.compile` → eager PyTorch. If a particular shape, dtype, or dropout combination isn't suited to the fused kernel, it automatically falls back — no manual switching needed. The first time a new shape is encountered there's a JIT/tuning warmup; after that it reuses the cache in the project's `.cache/triton`.

Plain LoRA / LoHa / LoKr / DoRA can use the official fused path; plain T-LoRA keeps the timestep rank mask and calls the official fused bypass that doesn't materialize a separate `ΔW`. `T-LoRA + Ortho` uses the project's own Cayley/SVD parameterization, doesn't pretend to be a LyCORIS algorithm, and so currently doesn't go through these fused kernels.

These numbers only speed up the adapter computation, not the entire training step by the same multiple — model attention/MLP, data loading, and sampling are usually still the main time cost.
