# 0013 — Move changelog into the announcements system (remove release_notes.yaml + old endpoints)

**Status**: Accepted
**Date**: 2026-06-28
**Decision makers**: @WalkingMeatAxolotl
**Related**: Announcement bar design [`docs/todo/announcement-center.md`](../todo/announcement-center.md) (Phase 2)

## Background

`release_notes.yaml` was the single source of truth for the changelog (a single file, structured `kind/summary/detail` entries), consumed by:

- `tools/bump_version.py` → validates and derives `CHANGELOG.md` (grouped by kind);
- `studio/services/release_notes.py` + `/api/system/release_notes{,_all}` → rendered by the frontend in the Settings version section + history modal.

After the announcement bar (announcement-center Phase 1) shipped, update announcements and migration notices moved to `docs/announcements/`, one file per post. The user decided to **also fold the changelog into the announcement bar**: one file per version, `tag: release`, browsable directly on GitHub; a single yaml file was getting hard to maintain and hard to browse historically as versions accumulated (already 24).

## Decision

1. **Data migration**: the 24 versions in `release_notes.yaml` → one post per version at `docs/announcements/<date>-v<version>.md` (`tag: release`, `version` set to that version). Body content is markdown converted from the original structured entries (kind groupings preserved as `**Added**`-style subheadings + bullets + detail). **Migrate the source language content first**; English backfill happens in Phase 3. **Delete `release_notes.yaml`** once migration is done.
2. **`bump_version.py` refactor**:
   - `render-changelog`: now generates `CHANGELOG.md` from `release`-tagged posts under `docs/announcements/` (sorted by version, descending; each version's body concatenated with a version header).
   - `validate`: now validates `release` post frontmatter (version/date/tag/title all present, filename consistent with version, version ordering).
   - `bump` / `verify-versions`: version-number sync logic unchanged.
3. **Remove old backend**: delete `studio/services/release_notes.py` + the `/api/system/release_notes` and `/api/system/release_notes_all` endpoints + their serializer. The announcement bar (`/api/announcements`) becomes the sole source.
4. **Frontend**: `SystemSection` drops the release-notes display + history modal (keeps update check / update / rollback); the version section gains a "View release announcements" entry that opens the announcement bar (default filtered to `release`). Remove `getReleaseNotes/getAllReleaseNotes` from `client.ts`, the `ReleaseNotes*` types, and related i18n.
5. **Docs**: retire `docs/release-notes-spec.md` (author guide consolidated into `docs/announcements/README.md`); rewrite the release process in `CONTRIBUTING.md` (releasing now means adding/editing a `docs/announcements/<version>.md` post, not editing the yaml).

## Rationale / trade-offs

- **One file per post, readable on GitHub** was an explicit user requirement; a single yaml file was hard to maintain.
- **Rejected**: rendering `CHANGELOG.md` grouped by kind with strict validation (`summary≤80` / kind whitelist / `pr_refs`) (Q1 already decided in favor of free-form markdown bodies for GitHub readability + one file per post). The migration keeps the kind subheadings, so grouping information from the historical changelog isn't lost — it's just no longer tool-enforced.
- **Removing the endpoints**: the announcement bar already covers "see what's new"; having both systems in parallel is duplication. The old endpoints only read the local yaml, so removing them has no known external consumers (only this repo's own frontend used them).

## Consequences

- Release process changes: maintainers write a markdown post when releasing, instead of editing a block at the top of the yaml. CONTRIBUTING updated accordingly.
- `CHANGELOG.md` content shape changes (grouped-by-kind → concatenated per-version bodies); still auto-generated, still usable as the GitHub Release body.
- The one-time migration script produces 24 `release` posts (in the source language); Phase 3 adds the English versions.
- The frontend version section is simplified; "what's new" is now handled entirely by the announcement bar.

## Decided (2026-06-28)

- **Q-A | CHANGELOG.md**: **Keep it**, auto-generated by `bump_version` from release posts (concatenated per-version bodies).
- **Q-B | bump_version validation**: **Keep light validation** — `validate` checks release post frontmatter (version/date/tag/title all present, filename consistent with version, version ordering unique).
- **Q-C | Split into multiple PRs?**: **One atomic PR** (data migration + tooling + endpoint removal + frontend changes must land together, otherwise the intermediate state breaks).
